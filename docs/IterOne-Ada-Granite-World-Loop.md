# IterOne-Ada-Granite-World-Loop

## Outcome after six passes

Ada makes a real Granite 4.0 350M decision inside MochEpoch's CSV-backed game loop in a browser on the Linux development laptop. In the seed room, the player asks Ada for the stone. Witness constructs one scoped call from current CSV; Granite returns the fixture's JSON action; game code checks and executes it; the saved stone CSV and visible holdings agree. After closing and reopening the game, the next interaction is built from the changed CSV with no retained model conversation or hidden game state.

This is the first working NPC transition on which later game interactions can build. It does not claim that other NPC behavior or civilization-like play has been demonstrated.

## Starting point and rules

- `predev` begins at `main` commit `214c0c66faaf4b778b05439760ff66654d688ddf`. The locked `docs/GAME_BLUEPRINT.md` blob matches `docs/ARCHITECTURE_LOCK.json` at `5a3e9ae1a5e0d3bcc058ffab599c7cb8d65f0945`.
- The existing six-file `world/` seed, CSV reader/display, and Chrome projection evidence are the game starting point. The Granite runtime, browser installation, CSV persistence, and phone evidence on `experiment/granite-single-ort-dual-session` at `b56215858213fe411969e40ece6284d1a7b45a84` are implementation references. Its Claptrap retrieval, dual-session, and 100-token conversation protocol are specific to that experiment.
- Repository `world/` files are the seed. Gameplay reads and writes one browser-persisted CSV working package initialized from that seed; static HTTP files cannot be changed by an in-browser action. Rendering and Witness must read the active package after initialization.
- CSV remains the only continuing game truth. Witness selects and constructs one call; Granite proposes an action; the concrete mechanic decides whether the world changes. The `hand_over | wait` schema is local to this fixture.
- Each pass asks one question, runs the smallest executable change, saves the actual input/output and result, tries a relevant failure, and reports only what that run establishes. A failed gate stays open. Before implementation changes, use the repository's `scratchpad/WORK.md` proposal and matching review or explicit active-conversation authorization for that specific proposal.

## Six passes

| Pass | Question and operation | Evidence and pass gate |
| --- | --- | --- |
| **1. Granite call** | Can the pinned Granite 350M browser artifact complete one fresh, single-session call using the intended tokenizer/template, graph, quantization, backend, and generation settings? Adapt only the model-loading and call path needed from the experiment branch. Record WebGPU and WASM as distinct configurations if both are tried. | Save exact model/runtime revisions, device/browser, formatted input, raw output, token counts and timings or failure. A completed, parseable fixture JSON response on the development browser passes this gate. Loading weights alone does not. Try a cold reload and record the first failing boundary if it fails. |
| **2. Witness scope** | Can the current `world/world.csv` index resolve the world description, Ada, player, stone, and interaction configuration into exactly one call packet without a parallel world model? Run the packet through the admitted Granite call. | Save retrieved CSV paths/values, packet, formatted model input, and raw response. Changing the stone holder in a disposable seed copy must change the packet; an unrelated fact added to that disposable copy must stay out. A missing or ambiguous scoped lookup fails explicitly. |
| **3. Ada decision** | Can Ada's real response be consumed as the fixture's `hand_over` or `wait` JSON action from one call, with no prior model conversation supplied? Keep extraction and parsing local to this interaction. | Save generated-only bytes, parsed action or exact parse failure, and the selected code path. A valid real response passes the decision gate. `wait` remains a recorded no-op; malformed, truncated, or extra-content output makes no world write. Do not sample repeatedly and report only a favorable output. |
| **4. Physical consequence** | If Ada says `hand_over`, does the mechanic check current active CSV facts, change only the active `world/objects/stone.csv` `holder_name` from `ada` to `player`, commit that CSV working package, and render holdings from the committed text? | Save before CSV, raw decision, physical checks, exact diff, committed after CSV, and visible result. One real Granite-driven transfer passes. A stale holder, double submission, or failed save must not produce a false success or a duplicate commit. If Granite chooses `wait`, preserve that outcome and keep this gate open. |
| **5. Fresh second interaction** | After discarding transient packet, parsed world, and model conversation and reopening the page, does the next call read the saved active CSV package? | Before calling Granite, the player visibly holds the stone from CSV. The new packet states `holder_name=player`; one new real call is consumed against that state. A repeated `hand_over` attempt cannot transfer the stone again. Save both calls and both CSV snapshots. |
| **6. Browser proof and breakage** | Does the complete path survive a fresh Linux browser session and the failures most likely to invalidate the result? Run the successful sequence there, then challenge invalid JSON, missing CSV reference, stale action, interruption/reopen, and storage read/write failure where reproducible. | Preserve a compact run record with exact code/model revisions, packets, raw responses, CSV before/after, visible result, and each challenge's observed outcome. The iteration passes only when a real Granite-driven handover and fresh second interaction succeed from active CSV and failures do not invent world changes. Record Android Chrome verification separately when available; it is required before claiming the same behavior on the phone. |

## Exit record

Record for each pass: commit, actual browser/device, question, input, result, CSV effect, saved evidence path, break attempt, and remaining limit. At the end, state separately what was demonstrated on a laptop browser, on Android Chrome if run, and only in synthetic checks. The next iteration can then broaden Ada's actions or add another actor based on this demonstrated loop.
